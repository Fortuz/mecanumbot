Reading this page

  

    
OK
        Publishing within tolerance of the nominal rate.

    
SLOW
        Publishing, but below tolerance. The node is running and falling behind —
            usually CPU contention or a blocked callback.

    
FAST
        Above tolerance. Informational; normally means the nominal figure here
            is stale relative to a retuned timer.

    
IDLE
        Silent, but silence is this topic's resting state and it is still
            wired up. Not a fault: the command topics are idle whenever nothing
            is driving the robot, and the people topics whenever nobody is in
            view.

    
DEAD
        Nothing on the graph holds the topic up, or nothing was received
            recently enough to measure. Check the node actually started.

  

  

    Topics with no nominal rate are event-driven — /cmd_vel only
    publishes while something is driving — so they are judged on staleness alone
    and never read SLOW.
  

  

    Pubs and Subs count the other nodes on
    each end; this page's own monitoring subscription is discounted. One of the
    two decides the topic's fate, and the other is dimmed. For most topics it is
    Pubs: the node producing the data is running. For the command
    topics it is Subs, because nothing publishes /cmd_vel
    or /cmd_accessory_pos while the robot stands still — the only
    evidence the link is intact is that the driver is still listening, so DEAD
    there means a command would go nowhere.
  

  

    Navigation stack is the study nav2 stack — AMCL, the map
    the Wi-Fi network selects, the planner and controller. Restart
    stops it wherever it was started (the base launch, or an earlier restart
    from here), waits for its nodes to leave the ROS graph, and launches
    mecanumbot_bringup nav2.launch.py again, so it also brings nav2
    back after a T1 pass. It is refused while a behaviour tree or a T1 pass is
    running. A stack relaunched from here stops when this web node does.
  

  

    The LED panel is read from the get_led_status service, which is
    a serial round trip to the Arduino Nano, so it is polled far more slowly
    than this page refreshes and can lag a change by a second or two. The
    movement panel shows commanded velocity from /cmd_vel
    beside measured velocity from odometry: a command with no
    measurement under it is a drivetrain fault that no topic rate would reveal,
    since both topics stay perfectly healthy while it happens.
